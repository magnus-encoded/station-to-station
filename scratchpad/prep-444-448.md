## #444 — usefulness receipts + neighbour priority

### Acceptance criteria (verbatim intent)
- Emit usefulness signal when a received fact is **promptly** recognised as from a Contact; credit the **immediate delivering neighbour**. Later attribution must not retroactively claim fast delivery.
- **Binary, decaying** boost among **currently visible** neighbours; **random** tie-breaks; no single-winner concentration; no name/key ordering.
- Receipts separate from direct witnessing and delivery guarantees; a receipt **does not retire** the referenced envelope.
- Storm gate preserved (2nd copy stops handing out); no peer-inventory exchange prerequisite.
- Gig-end message expiry separate from shorter local carry/outbox retention; best effort, may discard.
- Both platforms, bounded resources, useful diagnostics; no security promises about anonymous flooding.
- Parameters (15-min carry, 2-min usefulness) must not be presented as settled.
- #448 comment: participation policy (check-in start, 30-min grace ≤06:00, no active Gig = no radio, incoming traffic cannot extend) is separate from carry TTL/usefulness decay.

### What exists
- Receipt kind validated: `A/data/gossip/PublicGossip.kt:103,108`; `I/Data/Gossip/PublicGossip.swift` (same checks).
- One-hop admission (receipt only from its author): `PublicGossip.kt:198`; Swift equivalent ~l.160.
- Receipt not stored as fact, not held: `PublicGossip.kt:204,206`; `PublicGossip.swift:166`.
- Usefulness storage: `useful` map `PublicGossip.kt:170`, write `:210` (`useful[text] = min(expiresAt, now+120000)` — hardcoded 2 min, keyed by receipt `text`); prune `:192`. Swift `PublicGossip.swift:133,155,175`.

- Test: `PublicGossipTest.oneHopControlsRequireTheirAuthorWithoutPoisoningTheStormGate`; device test `GossipRadioDeviceTest.indirectControlsAreRejectedWithoutPoisoningDirectDelivery` (asserts one usefulness credit).

### Missing
- **No receipt is ever authored** (no `kind = "receipt"` construction in main sources on either platform).
- No "prompt" recognition window / receive-time vs recognition-time check; delivering neighbour not recorded per fact (only `delivered` set of peers we sent to; `PublicHeld.delivered` seeded with `from`).
- **`offer` ignores `useful`**: per-peer offer sorts by createdAt/id (`PublicGossip.kt:213-218`, `PublicGossip.swift:178-183`). No ordering of *visible neighbours* at all; radio serves whoever connects. Priority must live where the central picks which peer to connect/push to (`A/ble/GossipRadio.kt`, `I/Data/Gossip/GossipChannel.swift`/`GossipTransport.swift`).
- Earlier withdrawn attempt indexed envelope IDs instead of neighbour IDs — avoid (next-pass.md "Progress after the model restart").
- Diagnostics for receipts/priority; no sim-backed decay value (SWEEPS: usefulness window inconclusive).

### Early iPhone viability experiment (#448, #446 comment) — protocol
Pre-reqs: iPhone with debug build (sideload), Pixel 7 Pro with in-place install, Pi controller usable (`btmgmt info` shows index; BlueZ `Channels=1` wrapper `/home/pi/gossip-plain-att.sh`). Test Gig checked in on each phone, tonight, before 06:00. Log per trial: device states, timestamps, discovery delay, connection role, bytes, admitted IDs, persisted after relaunch.
1. **Locked receive**: iPhone checked in, app backgrounded (home), screen locked ≥2 min. Pixel (foreground, then background) authors a Log fact. Measure: discovery→connect→complete Pass time; fact present in iPhone ledger on unlock (unlock only after cutoff, e.g. 5 min). Directions: Pixel central→iPhone peripheral AND iPhone central→Pixel peripheral, separately.
2. **Locked forward to new peer**: with iPhone still locked, bring a *different, never-seen* peer (second Android or Pi GATT server / Pi peer) into range after step 1; that peer must receive the fact carried by iPhone (relay key, not author). Pass = new peer admits the exact envelope ID within e.g. 10 min, iPhone never unlocked.
3. **Two backgrounded iPhones** (when available): both locked; each direction.
4. Controls: foreground iPhone baseline; force-quit (expected fail — record, not a defect); Low Power Mode; after OS restoration (kill by memory pressure, not swipe).
- Repeat ≥5 trials each; report success n/5, median/max delay. **Pass**: steps 1 and 2 succeed in ≥ majority of trials within minutes with iPhone locked throughout. **Fail**: step 2 never succeeds while locked (routing then must assume iPhones are receive-only/foreground relays). Record ADR-0019 §6 expectation (backgrounded iPhone invisible to Android scanner) as a hypothesis to confirm/refute.
- Battery (screen off, same brightness/network, ≥1–2 h each, use device battery stats/mAh not %): gossip disabled; active no peers; active with traffic. Subtract baseline; state resolution.

## #415 — final-record statements diverging from implementation
- ADR-0019 "Still open": **"No user-facing off switch"** — Android notification stop exists (`GossipService.kt:99-101` → `GossipStore.stopParticipation`), iOS has `GossipTransport.stoppedAt` (`GossipTransport.swift:179`). (#415 comment item 3 left unchecked.)
- ADR-0019 §6 (~l.379-382, declared "unchanged" by amendment and by ADR-0021 "every word of §6 still holds"): service runs when device holds a **Contact** and is **carrying a live message**, in a night window, or **always relay**; "nothing schedules its shutdown". Now: check-in starts it, held envelopes/Contacts don't (`GossipPolicy.kt:55-67`), 30-min grace, manual stop.
- ADR-0019 §4 "held and offered to every **Contact** met before it expires" — now any peer, 15-min Carry window capped by expiry.
- ADR-0021 l.60-61 / "Related": parameters "**measured in** `sim/SWEEPS.md`" / "measured basis for the Carry window" — SWEEPS and wire spec say defaults are provisional; earlier sweep withdrawn; sparse sweep 0–16.67%.
- Wire spec l.60-61 "Usefulness lasts two minutes, binary, with random ties" — code stores 2 min but no random ties or priority exist; no receipts generated.
- CONTEXT.md l.176 receipt "saying something was useful" — fine as vocabulary, but no production path emits one; and l.179 Carry "two hops" framing vs sparse results.
- Missing from record (not wrong, absent): BLE challenge readable by unpaired strangers; message expiry vs outbox lifetime vs seen-IDs; plain ATT vs EATT limit; #448 lifecycle (Check in = start, Done = publication, grace, reopen→06:00, no-active-Gig shutdown).
