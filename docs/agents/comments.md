# Comments

A comment says what the code cannot: why it is this way, what it promises, what would break it. Everything else lives somewhere with a better home — the story in the commit and the PR, the behaviour in a test, the name in the name.

## Everywhere

- **Present tense, the code as it is.** No "used to", "now", "no longer", "was changed to", "previously", "fixed". The diff and the commit message carry the change; the comment describes where it landed.
- **No issue or PR numbers.** `(#166)` sends the reader away for an answer that should be here in one clause, or nowhere. Link an issue only for work not done yet, and only in a `TODO(#n)`.
- **Say it once, where it is decided.** A rule belongs on the function that enforces it. Callers do not repeat it; the other platform's twin carries the same comment, not a longer or shorter one.
- **Lead with the point.** The first sentence is the one a reader needs; if the rest can be cut without losing a reason, cut it.
- **Sacrifice grammar for concision.** Fragments are fine: "404 for empty list, not 200." beats a full sentence saying the same.
- **Domain words are exact.** Use the bold vocabulary from `CONTEXT.md` (**Gig**, **Line**, **Festival**) and mean it; it is not padding.
- **Delete with the code.** A comment whose declaration moved or went goes too. Never leave a doc comment above a blank line.

## Logic-layer functions

Rules, matching, merging, time, anything a test calls directly.

- **The doc comment is the contract**: what goes in, what comes out, what it refuses, in terms of the domain. Not how the body does it.
- **A rule stated as input → outcome is a test first.** "`Kjøkken Hagen` and `Kjøkkenhagen` are one name" is a test named for exactly that. Write the test; the comment only survives if it adds the *why* the test name cannot hold.
- **Keep the reasons nothing else records**: an external API's undocumented behaviour, a limit and where it comes from, the alternative that was rejected and the one-clause reason it loses. Write these as facts about the world, not as a story ("setlist.fm returns 404 for an empty attended list", not "we found out that…").
- **Inline comments mark the surprising line**, not each step.

## Plumbing

Wiring, transport, persistence, UI glue, platform APIs.

- **Default: no comment.** A well-named function that moves data from A to B needs nothing.
- **Comment only the trap**: a platform quirk, an ordering requirement, a threading or lifecycle constraint, a value that looks wrong and is not. One or two lines, then the code.
- **No restating.** If the comment could be regenerated by reading the next three lines, delete it.
- **No section banners** (`// ---- Tiles ----`). Split the file or the type instead.

## Tests

- **The test name is the rule**, in plain domain language: `a Gig whose automatic checks have stopped can still be pulled`. If a comment is needed to say what is being tested, rename the test.
- **No comments narrating the arrange/act/assert steps.**
- **A comment in a test explains only the fixture**: why this date, why this odd name, what real-world case the data mirrors.
- **No flavour text.** "Standing there is the strongest evidence the thing has begun" belongs in no file.

## Checking a comment

Before keeping a comment, it must pass all of these:

1. Is it true of the code as it is now?
2. Does it say something the names and the code do not?
3. Is none of it history, an issue number, or a restatement?
4. If it states a rule, is there a reason a test name could not carry it?

The periodic comment review asks these same questions, so a comment written to pass them will not come back in the report.
