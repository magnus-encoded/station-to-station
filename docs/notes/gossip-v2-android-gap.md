## 2. Correctness bugs

1. **`offer()` / `encodePublicGossipPass()` byte-budget mismatch can silently drop an entire Pass.**
   `offer()` (PublicGossip.kt:118-125) filters held envelopes against a hardcoded `bytes = 512` starting budget, assuming ≤256B `from` + ≤256B `proof` plus the `gossip-pass/2` header. But `encodePublicGossipPass()` (line 71-75) does the *real* assembly independently and then does `bytes.takeIf { it.size <= GOSSIP_MAX_WIRE_BYTES }` — if the real assembled size exceeds 40,000 (e.g. because `offer()`'s 512-byte guess undercounts real header/proof overhead, or plain off-by-one from newline-joining vs `size+1` accounting in offer()), `encodePublicGossipPass` returns `null` for the **whole pass**, not a trimmed one. Concretely: call `offer()` with envelopes that sum to exactly 39,900 bytes under offer()'s accounting; if the real proof string is 256 bytes (max allowed) and pushes the true joined size past 40,000, `encodePublicGossipPass` returns `null` and the peer gets nothing this cycle, even though almost all the batch was valid. Fix: either share one exact size function between `offer()` and the encoder, or have the encoder trim rather than reject.

2. **Duplicate-detection ordering discards legitimate late duplicates from a third party without crediting `held` state correctly in a subtle case.** Not a bug per se, but note: `receive()` calls `seen.containsKey` *before* checking `envelope.valid()` fully already happened above it — actually order is: `valid()` → time checks → `seen.containsKey`. That's correct order (spec requires the second copy be *valid* to close the gate) — verified against `alteredPayloadCannotCloseAnExistingStormGate` test, which passes. No bug there; flagging only because it's the single most safety-critical line and worth re-reviewing after any refactor.

3. **`gossipHash` uses `"%02x".format(it)` per byte** (line 59) — not a correctness bug, but see platform risk #2; at scale (called on every candidate envelope during signing *and* during every `valid()` call, which itself is invoked on every `receive()` and recursively for witness claims) this is a measurable perf tax on the BLE hot path on a phone.

4. **No overflow bug found in the `expiresAt - createdAt` cap** (line 40): since `createdAt < 0` is separately rejected and `expiresAt <= createdAt` is checked first, the subtraction can't be driven negative by attacker-supplied fields in a way that bypasses the 108,000,000ms cap. Fragile but not currently exploitable — flagging as a maintenance risk (should use `Math.subtractExact` defensively) rather than a live bug.

5. **`decodePublicEnvelope` formerIds empty-string case is handled correctly** (`f[2].split(',').filter{it.isNotEmpty()}` yields `[]` for `""`) — verified, no bug.

6. **Witness recursion is bounded to depth 1** — `claim.kind != "request"` is enforced before `claim.valid()` recurses, and a "request" envelope's own `valid()` never re-enters the witness branch. No unbounded recursion.

7. **Tab/newline injection after base64**: `text` and `attribution` are base64-encoded before being placed as tab-separated fields, so no injection vector there; the `fields().any { it.contains('\n') || it.contains('\t') }` guard (line 43) is therefore mostly redundant defense-in-depth, not a bug.

## 3. Wiring remaining to make this a real feature

Confirmed via grep: `PublicGossip.kt` and `GigIdentity.kt` are referenced **nowhere** outside themselves and their test file. Specifically:

- `GossipRadio.kt` (792 lines) has zero references to `PublicGossip`, `GigIdentity`, `PUBLIC_GOSSIP_HEADER`, or `PublicGossipState`. It only imports `GOSSIP_MAX_WIRE_BYTES` from `GossipWire.kt` (the v1 module) at line 29, and does its chunk assembly/empty-terminator framing at lines 105, 233, 755 against the **v1** wire format from `GossipWire.kt` / `GossipMint.kt` / `GossipToken.kt` / `GossipStormGate.kt` (data/GossipStormGate.kt, data/gossip/GossipMint.kt, GossipToken.kt) — none of which reference the new public types either.
- `TimelineStore.kt` (1342 lines) has zero references to `PublicGossipState`, `GossipEnvelope`, or `PublicHeld`. Its existing persistence pattern is `Json { ignoreUnknownKeys = true; encodeDefaults = true }` at line 672, used to serialize other `@Serializable` state classes (e.g. around lines 35, 53, 95, 130, 274, 353). `PublicGossipState` would need to be added as a sibling persisted blob the same way — this part should round-trip fine since kotlinx.serialization supports `MutableMap`/`MutableSet` of serializable element types, and `GossipEnvelope`/`PublicHeld` are both `@Serializable`.
- **No version negotiation exists.** There is nothing in `GossipRadio.kt` that distinguishes v1 (Contact-only) Passes from v2 (public) Passes on the wire. The v1 header is presumably a different literal in `GossipWire.kt` (`gossip-pass` at some version) vs the new `PUBLIC_GOSSIP_PASS = "station-to-station/gossip-pass/2"` constant (PublicGossip.kt:10) — since the header string itself is versioned (`/2`) and distinct from whatever the v1 header string is, an old client parsing a v2 Pass would fail its header-literal check and simply reject the whole Pass (fails closed, not misinterpreted) *provided* GossipRadio's dispatch tries the v1 decoder and gets a clean parse failure rather than a garbage partial decode. This needs to be verified by reading `GossipWire.kt`'s exact header string and the decode dispatch in `GossipRadio.kt` — not yet confirmed with a passing test. This is the single largest open risk: nothing currently calls `decodePublicGossipPass`/`encodePublicGossipPass` from the transport at all, so today an old and new client simply never exchange Gig gossip — the wiring gap is total, not partial.
- Exact call sites that must change in `GossipRadio.kt`: wherever it currently calls into `GossipMint`/`GossipStormGate`/`GossipWire` to build/parse a Pass for the Contact-only path, a parallel (or replacing) call into `PublicGossipState.offer()`/`.receive()`/`encodePublicGossipPass()`/`decodePublicGossipPass()` needs to be added, reusing the same chunk-and-empty-terminator write/read loop (GossipRadio.kt:222-249 read side, ~615-771 write side).
- Where projected facts reach the UI: `PublicGossipState.project(gigIds)` (PublicGossip.kt:127-134) is the only place that turns `facts` into a deduplicated, superseded-aware timeline — nothing in `TimelineStore.kt` calls it. This is the other half of "wiring" needed: a bridge from `PublicGossipState.project()` output into whatever `TimelineStore.kt` structure the Compose UI observes (likely one of the `@Serializable` state classes near line 35/95/130 — not confirmed by name, would need a follow-up read of `TimelineStore.kt`'s public API).

## 4. Android/Kotlin platform risks

- **`java.util.Base64`**: requires API 26. `minSdk = 26` (android/app/build.gradle.kts:43) — **not a risk**, exactly at the floor.
- **`"%02x".format(it)` in `gossipHash`** (PublicGossip.kt:59): `Int.format` boxes and goes through a `Formatter`/`Locale` allocation per byte, for a 32-byte digest that's 32 allocations per hash, and hash is computed on every sign + every `valid()` call (including the nested witness `valid()` call) — on a BLE gossip loop processing dozens of Envelopes per Pass, per peer, this is a real CPU/GC pressure point on a phone. Should be a direct hex-nibble lookup table instead.
- **`@Serializable class PublicGossipState` with `MutableMap`/`MutableSet` defaults**: kotlinx.serialization supports `Map`/`Set` (and their mutable subtypes) as long as key/value types are themselves serializable — `String`, `Long`, `GossipEnvelope` (`@Serializable`), `PublicHeld` (`@Serializable`) all qualify. Should round-trip correctly given the existing `Json { ignoreUnknownKeys = true; encodeDefaults = true }` codec used elsewhere in `TimelineStore.kt:672`. Not a risk, but should be verified with an actual encode/decode round-trip test once wired in (none exists today — `PublicGossipTest.kt` never serializes `PublicGossipState`).
- **Threading**: `PublicGossipState.receive()`/`offer()`/`prune()` mutate plain `MutableMap`/`MutableSet` with no synchronization. `GossipRadio.kt`'s GATT callbacks run on the Bluetooth binder thread pool, potentially concurrently with a UI-thread read via `project()`. If `PublicGossipState` becomes a shared mutable singleton (as `TimelineStore`'s other state classes likely are), concurrent `receive()` from one peer callback and `offer()` for another peer, or a `project()` call from a Compose `StateFlow` collector, race without any lock/mutex/single-thread-confinement visible in these files.
- **`GigIdentity`'s `store()`** touches Android Keystore (`KeyStore.getInstance("AndroidKeyStore")`) on every `publicKey()`/`sign()` call — each of those does a full `load(null)` + alias existence check; this is a slow synchronous call that must not run on the main/UI thread inside a Compose recomposition path, and nothing in `GigIdentity.kt` documents or enforces that constraint.
